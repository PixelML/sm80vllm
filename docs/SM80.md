# SM80 (Ampere / CMP 170HX) fork: provenance and status

This fork exists to run PixelML CMP 170HX (NVIDIA GA100 silicon, compute
capability 8.0, no FP4/FP8 tensor cores, no NVLink) on models whose upstream
vLLM support targets Hopper or newer. It is not a general-purpose vLLM fork;
it exists to carry Ampere fallback kernels that upstream does not (yet) ship.

## Branch `sm80` — base

- Base commit: `f8ea5bb163c161ef38b401d055cc5fd4a934091a`,
  "[Attention] DeepSeek-V4 sparse MLA on SM8x (A100/A800)".
- Lineage: this commit descends from the `haosdent/vllm` fork
  (`dsv4-flash-a100` line), which itself builds on prior Ampere DeepSeek-V4
  work credited to `allover326` and `Lasimeri` (Triton sparse-MLA kernel
  patterns, manual e4m3 bit tricks). See
  `PixelML/DeepSeek-V4-Flash-Vision-Exp-CMP-170HX` `docs/VISION-PORT.md` and
  the `club-170hx` evidence trail for the full history.
- Carries a working `vllm/models/deepseek_v4/ampere/ampere_sparse.py` SM80
  sparse-MLA attention backend, which the mainline `deepseek_v4` model does
  not have (mainline's sparse-MLA backends declare support only for compute
  capability 9/10/12).

### Consolidated onto this branch

`sm80` now carries, as separate commits on top of the base commit above:

- the 8-file DSpark-under-pipeline-parallelism patch set used by the
  published text image `ghcr.io/pixelml/club-170hx:vllm-deepseek-v4-sm80-20260902`
  (recovered from that image's build receipts,
  `dsv4-vision-exp-4card-20260902T0440Z/receipts/vllm-source-patches.diff`);
- the DeepSeek-V4-Flash-Vision-Exp reverse port (Path 3), four commits plus
  a fifth for the `load_weights` finalize fix — see
  `PixelML/DeepSeek-V4-Flash-Vision-Exp-CMP-170HX` `docs/VISION-PORT.md`
  for the full account;
- the `safetensors` F8_E8M0 overlay patch needed to load a checkpoint
  shard carrying a `ue8m0` block-scale tensor (`patches/`);
- two root-cause fixes from issue #79 for the vision build's two known
  crashes (see "Known limits" below).

`sm80` HEAD is now the exact source used to build
`docker/Dockerfile.sm80`; images no longer need bind-mounted fixes on
top of a pinned base.

### Build-time import gate scope

`docker/Dockerfile.sm80`'s final `RUN` step checks that `vllm`, `torch`,
and the compiled custom ops import. It does not import
`vllm.models.deepseek_v4` classes, because `docker build` runs under
the `runc` runtime with no NVIDIA driver visible, and that import chain
pulls in `vllm/v1/attention/ops/fp8_sm80.py`. That module's
triton-disabled fallback path calls `tl.constexpr` unconditionally,
which is not callable once `triton_utils` disables triton for a
missing driver — a pre-existing upstream gap, not one of this branch's
patches, that only shows up with no GPU present. Run the fuller check
after the build, with a GPU runtime, once one is free:

```
docker run --rm --runtime=nvidia <image> python3 -c "
from vllm.models.deepseek_v4.nvidia.model import DeepseekV4ForCausalLM
from vllm.models.deepseek_v4.nvidia.vl_model import DeepseekV4ForConditionalGeneration
from vllm.models.deepseek_v4.nvidia.dspark import DSparkDeepseekV4ForCausalLM
print('deepseek_v4 text + vision + dspark import OK')"
```

### Known limits (vision build)

- **`c>=4` crash**: an EngineCore/`shm_broadcast` timeout at concurrency
  4 and above, root-caused to a stale CUDA-graph padding row and fixed
  on this branch. See
  [seanphan/pixelml#79](https://github.com/seanphan/pixelml/issues/79)
  for the RCA and the patch commit on this branch
  (`vllm/v1/worker/gpu/model_runner.py`, "RCA Bug A").
- **131k-token crash**: prefill past 65,000 tokens crashed the engine
  with a Triton illegal-memory-access in the DSpark drafter, root-caused
  to an out-of-bounds read on a fully-rejected chunk and fixed on this
  branch. See
  [seanphan/pixelml#79](https://github.com/seanphan/pixelml/issues/79)
  for the RCA and the patch commit on this branch
  (`vllm/v1/worker/gpu/spec_decode/dflash/speculator.py`, "RCA Bug B").
- Neither fix has a GPU boot verified against it yet on this branch as
  of this commit; both patches are the evidence-backed primary
  hypothesis from the issue #79 RCA, applied as static source changes.
  Re-run the `c>=4` ladder and the 131k-token prefill test on the next
  vision-server boot window to confirm.

## Branch `glm53-sm80` — GLM-5.3-Flash port

Base commit: `3bec275739` (wtdcode/vllm-backport `master` tip,
"scheduler: recover from invalid KV blocks on hybrid memory allocator").
**Not** a descendant of `sm80` — wtdcode's GLM-5.3-Flash Ampere enablement
has an independent lineage from our DeepSeek-V4 sparse-MLA base. The two
branches share only the general SM80 sparse-MLA technique, not a common
git ancestor. See the issue #103 comment for the full port plan,
Hopper-dependency inventory, and hours estimate. Summary of the base
decision: neither applying vLLM PR #53906 (`glm5_next` support) directly
onto `sm80`, nor reverse-porting `sm80`'s fallbacks onto the PR head,
was the starting point. A third-party fork, `wtdcode/vllm-backport`
(Apache-2.0), already carries a working Ampere/SM80 build of `glm5next`
including a generic Triton sparse-MLA backend
(`vllm/v1/attention/backends/mla/triton_mla_sparse.py`) built on the
identical `ampere_sparse.py` file this fork already has. This branch vendors
those already-Ampere-adapted files from `wtdcode/vllm-backport` rather than
re-deriving Ampere fallbacks from scratch. Every vendored file is listed
with its wtdcode commit reference in the commit that adds it.
